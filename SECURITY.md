# Security policy

Agent Quality Toolkit handles signatures, hash chains and sandbox boundaries, so security reports are welcome.

## Reporting a vulnerability

Please use GitHub's private vulnerability reporting ("Security" tab → "Report a vulnerability") instead of a public issue. Include the package, version, a description and, if possible, a reproduction. You will get an answer within two weeks.

## Scope

In scope: signature and chain verification that accepts tampered records, signature statements that can be replayed or rebound to other content, agent-context checks (`require_human`) that an agent can bypass without operating-system access, sandbox escapes in aqt-sensei, and secrets reaching evidence records.

Out of scope: attacks that need the owner's private keys or passphrases, root on the host, or a modified installation; detector evasion by adaptive prompt injection (detectors are a triage layer, see the README's honest scope).

## Threat model in brief

The adversary is an AI agent that runs as your Linux user: it can read and change what you can, but it does not know your passphrase. The passphrase-protected key is the real control for human decisions; the check for an agent session is a guard, not a boundary. In the default user mode the toolkit is tamper-evident, not tamper-proof: an agent can read the trail writer's service key, so a re-signed edit is found only by head copies kept on another device or by RFC 3161 time stamps made after it. Separate-user mode for the trail prevents that.

Since the October 2026 review and its fix rounds:

- **Keys.** Passphrase-protected keys use scrypt and AES-256-GCM. Keys from earlier versions are re-encrypted at their next use or with `aqt-signoff rekey`; backup copies of those older key files keep the weak encryption, so replace them.
- **Enrolment is counter-signed.** `signers.json` is configuration, not trust. A key counts only when the evidence (the trail, when there is one) holds its own signed enrolment request and, for everyone except the very first signer, an approval by an enrolled signer made with that person's passphrase (`aqt-signoff signers approve`). A key an agent creates and enrols itself stays *pending*, and a copy of an enrolment request counts once. `aqt-signoff signers export` writes the registry together with these records, so that someone on another machine checks the keys the same way. aqt-signoff, aqt-trail (review signatures), aqt-quarantine (decisions) and the aqt-ui record inspector apply these rules when aqt-signoff is installed; without it, aqt-trail and aqt-quarantine rest on `signers.json` alone and say so.
- **Limits of the enrolment check.** The first enrolment of an empty evidence store counts without approval: enrol yourself first and check the first signer that `aqt-signoff signers check` and `aqt status` name. After every key was revoked, the next new key counts without approval (a *re-bootstrap*, so that a solo owner can recover). `signers check`, `aqt-signoff verify` and `aqt status` keep flagging it for good: only a key that counted before it could confirm it, never a key it approved. A forged unsigned revocation of every key followed by a new enrolment looks the same; `signers check` reports every revocation that neither the revoked key nor another counting key signed, and the re-bootstrap warning names those before it. Treat an unexpected re-bootstrap as an incident, and enrol a second person in time, so that a lost key is replaced through an ordinary approval. Without a trail, an agent can reorder or delete records in the plain evidence file. After adding aqt-trail later, run `aqt-signoff signers import` once and read its preview; a second import is refused, and records added to the old file later are never imported.
- **Signatures count once.** A copy of a signed statement in another record is a replay (`invalid`), and a copied audit-trail review counts once. A quarantine decision acts only through what it signs, once, in the order it was signed.
- **Verification is strict.** `aqt-evidence verify` and `aqt-trail verify` accept only canonical record lines, and `--require-signature` needs `--key`.
- **Bundles need explicit trust.** `aqt-trail verify --bundle` trusts only the service key, time-stamp CA and signer registry you pass (`--pin-key`, `--tsa-ca`, `--signers`), never the copies inside the bundle.
- **Test time stamps count only in test mode.** Any client may ask the writer for a TEST ONLY time stamp; it counts as an anchor only with `--test-tsa` or `[anchor] test_tsa = true`. aqt-ui shows test mode, and review parameters that differ from the built-in defaults, before you sign a review.
- **Attribution is a heuristic.** The trail writer records how far it could follow the sender's process chain (`observed.chain_status`), and a record that claims a person counts as attributed only with a complete chain without an agent in it; a record pushed through the writer's drain operation is judged by the process that pushed it. A process started with `setsid -f`, `systemd-run --user` or `tmux send-keys` into a person's shell can still look complete.
- **Change control with the trail.** With aqt-trail in use, aqt-change counts a receipt or review only when the trail holds the same record, received from its sender over the writer's socket. Commit `require_trail = true` and the writer's key id (`trail_keys`) in the project's `.aqt/change.toml`, so that the agent's environment can neither switch this check off nor point it at a log the agent wrote; gate policy committed there cannot be relaxed by the user configuration. The tree fingerprint hashes every tracked file instead of trusting `git status`; only `.gitignore` files that are part of the repository leave a file out of it; every check run gets a fresh, empty Python bytecode cache; and `finish` refuses to leave a tested change out of its commit. The plan's base commit is checked against its `begin` record, so editing it does not drop the project settings (`plan_base_mismatch`). Limits: a same-user agent can still send a made-up receipt through the socket (the trail keeps its process chain); in user mode it can read the service key, so the key pin is real only in separate-user mode; aqt-change's local copy still decides which records belong to a project; ignored files that a run may load besides Python bytecode (compiled modules, other tools' build caches, the virtual environment) are not checked. A gate is only as trustworthy as the environment and the working tree it runs in: run the gate that decides on a clean checkout in CI.
- **The local web page.** The aqt-ui cookie alone is no session: every request also needs a session key that the page keeps per browser tab. A release is offered only after every page of the held content was shown in that session; a threat may be declared from the highlighted passages, because it keeps the content withheld.

The full list of limits is in the [review report](docs/security-review-2026-10.md#limits-that-remain) and in the "Threat model and limits" section of each package README.

## Review status

In October 2026, AI reviewers running models from two vendors reviewed the code at commit `363b445` from the position of a same-user agent. This was an AI-assisted review, not a professional security audit. Fresh AI verifiers then checked the fixes twice; each time they found most of them sound, some only partly, and some new problems, which three further fix rounds addressed. After four fix rounds and two verifications, no open high-rated finding is known; the fixes of the fourth round have not been verified yet. Every finding, its fix or documented limit, the verifications and what remains open are in the [review report](docs/security-review-2026-10.md).

Version 0.1 is a preview.
